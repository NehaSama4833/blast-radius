# Blast Radius: how it works (plain language)

This file grows with the code. Written so Neha can explain every part. Last updated: Day 1 (Thu 15 Oct).

## The one-sentence idea

A company is a web of things that depend on each other. When many alerts fire at once, we use that web (a **graph**) to find the one thing that best explains *all* the alerts, even if that thing is not alerting itself.

## What a graph database is (and why FalkorDB)

Normal databases store tables. A graph database stores **nodes** (things: a service, a person, a deploy) and **relationships** between them (`payments-api DEPENDS_ON ledger-svc`). Questions like "everything that would break if this database died" are just *follow the arrows*, which a graph database does very fast. We use **FalkorDB** and ask questions in a language called **Cypher**.

## The pieces built on Day 1

### 1. The fake company ("world") — `backend/world/`

We can't use a real company's data, so we generate two fake ones, **deterministically** (same random seed means the same company every time, so tests never flake).

- **acme**: a payments company, 30 services in four layers (edge, api, core, data).
- **globex**: a logistics company, 15 services with a deeper, different shape, so nothing we build works only for one layout.

Files: `acme.py` and `globex.py` hold the fixed layout (who depends on whom, which teams, people, features, customers). `history.py` generates 90 days of history from it: about 476 deploys, 26 past incidents with their fixes, and **three planted repeating problems** (ledger-db connection pool, kafka rebalance, auth-svc certificate) so the "History" agent has real patterns to find. `loader.py` writes the world into FalkorDB.

Two details worth knowing:
- **Dependency arrows point from the dependent to the thing it needs.** `payments-api -> ledger-svc` means payments-api breaks if ledger-svc breaks. Kinds: **sync** (calls it and waits; breaks immediately) and **async** (a queue; falls behind, shows up as "lag").
- Some data stores are **`monitored: false`**: they have no alerts of their own. That is how a database can be the real cause while only *other* services shout.
- Times are stored as "seconds ago" and turned into real timestamps when loaded, so "deployed 41 minutes ago" is always true.

### 2. Schema and indexes — `backend/graph/`

`db.py` connects (embedded FalkorDB locally, or a real server when `FALKORDB_URL` is set). `schema.py` creates **indexes** (like a book's index, they make lookups fast) and a **full-text index** on `Incident.summary` so we can search past incidents by words. Indexes are created *before* loading data because the full-text index only sees nodes added after it exists.

### 3. The failure model — `backend/world/failure.py`

`break_service(world, service, change_kind, noise)` is the single answer to "if X breaks, what happens?". It:
1. creates the bad deploy 20 to 60 minutes before the first alert;
2. fires alerts on every **monitored** service that depends on X through sync links;
3. fires delayed **lag** alerts on services that depend on X through queues (async);
4. does **not** alert for X if X is unmonitored (the hidden culprit);
5. optionally adds noise: one unrelated flaky alert, one missing alert, and innocent "distractor" deploys;
6. returns the **ground truth** (the real cause), which tests and the benchmark use to grade answers.

The chaos button, the benchmark and the tests will all use this same function.

### 4. Scenarios (the benchmark's questions) — `backend/world/scenarios.py`, `bench/scenarios/`

30 scenarios: **10 dev** (we may tune on these) and **20 held-out test** (reported numbers; never tuned on). Difficulty tiers: **easy** (one alert), **medium** (silent culprit 2+ steps down), **hard** (silent culprit + noise), **ambiguous** (two causes at once; the right answer is "more than one cause"). They were generated by a fixed seed and **committed before any ranking or agent run on the test split**. A test (`test_scenarios_frozen`) fails if the files ever change, and the ranking tests only use the dev split.

### 5. Root-cause ranking — `backend/tools/ranking.py`

Idea: a good culprit **explains every alert** and **does not predict alerts that are not happening**.

For each candidate service:
- *explains* = alerting services that depend on it (through sync links)
- *predicts* = monitored services that would break if it broke
- **coverage** = explained alerts / all alerts
- **precision** = explained alerts / predicted alerts
- **score** = F1 of the two (their harmonic mean, which is high only when both are high)

Why precision matters: `auth-svc` is used by almost everything, so it "explains" lots of alerts, but it would also break many healthy services, so its precision is low and it loses to the real cause. Ties go to a silent service deeper in the stack.

The **graph (Cypher)** finds who can reach whom; **plain Python** does the arithmetic (so the AI never does maths, and it is unit-tested).

Decisions where I interpreted the doc (please tell me if you disagree):
- *predicts* counts a service only if it is **monitored** (including the candidate itself). This matches the doc's example (ledger-db unmonitored, "7 monitored services should alert").
- **Async/lag**: the doc says "sync edges only", but the failure model also produces lag alerts for queue consumers. So a service with a direct async link to the candidate also counts as explained, and monitored direct async consumers count as predicted. Without this, a Kafka outage could never be found. The sync part is exactly as the doc says.
- `likely_multiple_causes` is set when no candidate explains at least 70% of alerts (the doc's rule). I also return `weak_fit` when the best score is below 0.7. On the one dev two-cause storm, a shared dependency covers everything so the 70% rule alone does not fire, but `weak_fit` does. The Lead agent (Day 2) should abstain or lower confidence on either flag.

### 6. The read tools — `backend/tools/read.py`, `registry.py`

Each tool is one parameterized Cypher question (values are passed as parameters, never glued into the query text, so nothing typed can change the query). Every tool returns data, the **ids of the nodes it read** (for the later "claims are verified" check), and a **receipt** (which tool, which parameters).

| Tool | Answers |
|---|---|
| `rank_root_causes` | which service best explains this alert storm |
| `blast_radius` | what breaks now (sync) vs soon (async), features, customers, ARR at risk |
| `dependencies` | what a service relies on |
| `recent_changes` / `change_details` | deploys just before the storm, and one deploy's author, diff and commits |
| `find_experts` | who to page; timezone-aware ("awake" = 08:00 to 22:00 local) |
| `similar_incidents` | past incidents on this service or neighbours, plus fixes (graph match + full-text search) |
| `lessons_for` | learned fixes (procedural memory) |
| `critical_services` | chokepoints (betweenness) and most depended-on services (PageRank) |
| `path_between` | shortest dependency path, used to explain a claim |
| `explore_graph` | read-only escape hatch: runs through `GRAPH.RO_QUERY`, so the database refuses writes |

`registry.py` lists all tools with JSON schemas and validates arguments. The agents and the MCP server will both use it.

### 7. Tests and CI

`pytest backend/tests` (101 tests): world determinism (even across Python processes), failure model rules, frozen scenarios, golden numbers for ranking, every tool, read-only enforcement, injection-attempt check, graph copy independence. GitHub Actions (`.github/workflows/ci.yml`) runs them against the real `falkordb/falkordb` Docker image. Note: Docker was not runnable in my sandbox, so the CI file has not been exercised yet; locally everything ran on embedded FalkorDB.

## Added later on Day 1 / early Day 2 (no API key needed)

### 8. The shared board and the citation check — `backend/agents/board.py`

The agents never talk to each other. They share a **board made of graph nodes**: an `Investigation` has `Hypothesis` nodes (the Lead's top candidates) and `Finding` nodes (what each specialist found, linked `SUPPORTS` or `WEAKENS` to a hypothesis). The Lead decides by reading the board with a graph query (`read_board`), never by reading specialists' chat.

Rules enforced in **code**, not in a prompt:
- **Scoping:** each agent can only call its own tools and only write its own kind of finding (Changes writes "temporal", History "historical", and so on). Only the Lead proposes actions and records the decision.
- **Citation check:** the server remembers every node id each agent was shown by a tool. A finding that cites an id the agent never saw is rejected (`CitationError`), as is a finding with no citation. The UI will show "claims verified: N/N".
- **Receipts:** each Finding and Decision stores which tools were called with which parameters, the graph version, and the node ids read, so an answer can be traced and re-run.
- **Abstaining:** the Lead may record `root_cause=None` ("undetermined") with low/medium confidence, but never high.

### 9. Memory write-back — `backend/agents/memory.py`

"Mark resolved" (a human click) turns an investigation into an `Incident` with a `Resolution`, and creates or updates a **Lesson** (for example "ledger-db: config change fixed by rollback", times seen, average time to fix). The next investigation finds it through `lessons_for` and `similar_incidents`. This is the "memory that changes behaviour" story. It is switched off during benchmarks, because the docs-only baseline has no memory.

### 10. Prove the fix — `backend/tools/verify.py`

`verify_mitigation` copies the graph (`GRAPH.COPY`), applies a proposed fix to the copy, and recomputes which alerts that one fault explains, using the same rule as the failure model (`alerting_for`). It reports which current alerts would clear, which would remain (for example a second cause), and a drain time for queue lag. It is a **simulation against the dependency graph**, and says so. The copy is deleted afterwards and the real graph is never touched.

### 11. Sandboxes — `backend/graph/sandbox.py`

Each visitor gets a private copy of a template world (`sbx_<id>`). Timestamps are shifted so "now" is true again, the copy expires after 2 hours, and at most 50 exist at once. The state lives inside the database (a `Meta` node), so it survives restarts.

### 12. MCP server — `mcp_server/server.py`

The same read tools, offered over the Model Context Protocol so Claude Desktop or Claude Code can investigate a graph (stdio, or `--http`). Read tools only; writes stay inside the app behind the checks above. Results include the `cites` list.

### 13. The investigation runner and the no-LLM policy — `backend/agents/runner.py`

`run_investigation` does: Lead ranks the storm and writes the top 3 hypotheses to the graph, then **Impact, Changes, History and People run in parallel** (four threads), each calling only its own tools and writing findings to the board, then the Lead reads the board from the graph, decides, checks the fix with `verify_mitigation`, and drafts the incident message. Every step is also sent out as a live event (for the screen).

How the agents *think* is a separate, swappable "policy". The one built so far, `RulePolicy`, is **deterministic and uses no AI**: it makes the tool calls a careful engineer would and applies plain rules (for example "high confidence only if the fit is strong AND a deploy preceded the storm AND there is a precedent"; "abstain if no single service explains the storm"). It lets the whole pipeline run and be tested without an API key, and it is a useful comparison later (graph tools without the LLM). The Claude-backed policy (needs the key) plugs into the same place. I only ran it on the 10 **dev** scenarios; it finds the true cause in all 9 single-cause ones and abstains on the two-cause one. The held-out test scenarios have not been run.

### 14. The web API — `backend/app/main.py`

FastAPI. No free text anywhere: every input is a pick from a list, checked against the graph. `/api/sandbox` makes a private copy, `/api/chaos` breaks a service (or "Surprise me") and **never reveals the culprit**, `/api/investigate` streams live events (SSE), `/api/resolve` stores the lesson, `/api/post` sends the **server's own drafted message** to Discord (the client cannot send text, so nobody can make the app post arbitrary content). Protections: per-IP rate limit, a daily investigation cap, and a **replay fallback** (a recorded investigation, clearly labelled "replay") when the cap is hit. Discord posting only accepts real `discord.com/api/webhooks/...` URLs and never allows mentions like @everyone. The current replay was recorded from the no-LLM policy; I will re-record it from a real Claude run once the key is in.

### 15. The model layer — `backend/agents/llm.py`

One small interface over two kinds of provider: Anthropic's API or any OpenAI-style API such as OpenRouter. The agents ask for a "completion" and never care which is used. It also has the **tool loop**: the model may call tools until it answers, with a cap on steps and output tokens, and errors in a tool call are handed back to the model so it can fix them. The key is read only from environment variables, is never printed, and is never stored in the repo. Tested with fake provider responses. Not yet tested against a real model: this sandbox's network policy blocks OpenRouter, but reaches Anthropic's API.

### 16. The benchmark harness — `bench/`

- `bench/docs.py` is the **docs-only baseline** (condition B): the same facts as the graph, written as Markdown pages (service pages, team pages, deploy log, postmortems, runbooks, the live alert log), plus a plain BM25 keyword search (`search_docs`) and `read_doc`. No graph and no dependency traversal, like a typical "search the wiki" agent.
- `bench/metrics.py` scores each scenario: top-1 and top-3 root cause, was the triggering deploy found, invalid citations, correct and wrong abstentions, and calibration (are "high" verdicts right more often than "low"?), per difficulty tier.
- `bench/run.py` runs a split. **It refuses the held-out test split unless `--final` is passed**, so nobody tunes on it by accident. Each scenario gets its own fresh graph, and memory write-back is off, because the baseline has no memory.

Honest note on the numbers: the rule-based policy was written while looking at the 10 dev scenarios, so its perfect dev score is a sanity check, not evidence. Only the one-time final run on the 20 test scenarios counts, and it will be reported whatever it shows. The with-a-real-model conditions (graph agents vs docs-only agent) are added once the key works.

## 17. The Claude-backed agents (written, tested only with a fake model)

`backend/agents/llm_policy.py` plugs into the same slots as the rule policy. Each specialist is a Claude (Haiku) loop that can only call its own tools, then writes findings as JSON. Safety rails, all enforced by our code, not by trusting the model:

- A finding is stored only if every id it cites appeared in that agent's own tool results; otherwise it is thrown away and counted as rejected.
- The numbers that feed the verdict and the Discord draft (impact, deploy, precedent, who to page) are read from the tool results, never from the model's words.
- The Lead (Sonnet) must pick one of the hypotheses on the board or say undetermined. If the structural ranking says "likely more than one cause" the model is not asked: the answer is undetermined. "High" confidence is downgraded unless the fit is strong and a change lines up in time.
- If a model step fails (bad JSON, API error) that step silently falls back to the rule policy and the audit trail says so.

The docs-only baseline (`bench/baseline.py`) is the comparison: same facts as Markdown files, keyword search, same Lead model, no graph, no simulation, no memory.

Everything here is tested with a scripted fake model. It has NOT been run against the real API yet (no key), so prompts will need tuning on the dev scenarios only. When an API key exists, the web API uses these agents automatically (set USE_RULES=1 to force the rule policy).

## 18. Extra features (from the design doc's "could ship" list)

**Coverage-only ablation (`graph-coverage-only`).** The same graph tools and rule policy, but candidates are ranked by coverage alone, without the precision part of the score. Comparing it with `graph-rules` shows how much of the result comes from walking the graph and how much from our scoring formula. On the dev scenarios only: 8 of 9 single-cause storms correct without precision, against 9 of 9 with it. That is a dev number, not evidence.

**Two-cause split (`cause_set`).** When no single service explains the storm, `rank_root_causes` also tries a greedy split: take the best precise candidate, remove the alerts it explains, rank the rest. It accepts only if each pick is at least 70% precise, explains 2+ alerts, and together they cover 85%+ of the alerts. The Lead still answers "undetermined" but now adds the two leads. On the dev ambiguous storm it finds kafka plus a lead in the fraud area (the real second cause is a silent store one layer below, which the split names as the alerting service above it, so the text says "the second may sit a layer below"). It finds nothing on all 9 single-cause dev storms.

**Ripple (`backend/agents/ripple.py`).** A late alert after an investigation: re-rank with all alerts, then retire only the findings the new alert can change (findings whose receipt read a new alerting service, plus Impact findings on hypotheses whose explained-alert set changed). Changes, History and People findings are kept without re-running. Only the affected specialists re-run, only on the affected hypotheses; the Lead decides again. Retired findings and the old verdict stay in the graph (SUPERSEDED_FOR, PREVIOUSLY_CONCLUDED). On dev scenarios with the last two alerts delivered late, the answer matches a from-scratch run, and in one case (dev-hard-4) it fixes a first guess that was wrong. Not wired into the web API or UI yet.

**docker-compose import (`backend/world/compose_import.py`).** Library and command line, not a web upload (the site has no free-text input on purpose). Depends_on becomes a sync edge, a broker dependency becomes an async edge, a missing healthcheck means "unmonitored", the layer is guessed from the image. It prints what it assumed.

## 19. Ask the graph, bring your own system, and the demo moments

**Ask the graph (`/api/ask`, `backend/agents/ask.py`).** The one free-text box on the site. A small model (Haiku) answers using only the read-only graph tools, in at most 5 steps. Its citations are checked like the agents': ids it never read are dropped and counted. Rate limited to 6 questions a minute per visitor and counted against the daily cap. Without a model key it says so and everything else still works.

**Bring your own system (`/api/import`).** A pasted docker-compose.yml (max 20 KB, 80 services) becomes a private sandbox graph using the compose importer; the world description is stored on the sandbox's Meta node so the failure simulator can break it. Surprise mode adds no noise on these small graphs.

**Demo moments.** `/api/whatif` (click a node: what breaks if it fails), `/api/late` (fire the alerts that the failure should have raised but were missing, then Ripple), `again` on `/api/chaos` (repeat the last break after resolving: the History agent cites the lesson just written). A new break or a resolve marks earlier alerts resolved, so storms never pile up.

## 20. Fact-checking, postmortems, a real topology and scale (Oct 16)

**Fact-checking (`backend/agents/faithful.py`).** Free text is the one place a model could slip something in. After every investigation we scan the verdict's reasons and every finding: each service name, deploy id (d-N) and incident id (INC-N) must be a node that the writer saw (in a tool result, or in the alert list every agent is given), and each number above 10 must appear in some tool result (as a value, a list length, a percentage of a 0-1 score, or inside a returned string). Small numbers are skipped because "3 findings" would cause false alarms. The UI shows "Fact-checked" or lists what was not found; the benchmark counts flags. The rule policy's template text passes with zero flags on all dev scenarios (a sanity check of the checker). The same check runs on Ask the graph answers.

**Postmortem (`backend/agents/postmortem.py`, `/api/postmortem/...`).** A traversal of the investigation's nodes rendered as Markdown: summary, timeline, reasons, hypotheses with each agent's findings, alerting services, the lesson saved, suggested follow-ups. No model is involved.

**Boutique world.** The call graph of Google's Online Boutique demo (frontend, checkout, cart, product catalog, currency, payment, shipping, email, recommendation, ad, redis-cart). We chose which services lack alerting (redis-cart, currencyservice) and invented teams, people and history; the edges are the project's.

**Scale.** `rank_root_causes` now visits candidates by coverage and stops once a candidate's best possible score (coverage with perfect precision) is below the current top-k, which gives exactly the same top-k (tested on 36 random storms over three worlds) with far fewer expensive blast-radius walks. Results in docs/SCALE.md.

## 21. The Auditor (`backend/agents/auditor.py`)

After the Lead decides, the simulation result and the fact-check are stored on the Decision node. The Auditor then reads only the graph (never the team's memory or transcripts) and checks: the Decision links to the blamed service; the accepted hypothesis has support from at least one specialist (two for high confidence, not counting People); a blamed deploy went to that service before the first alert; the simulated fix clears at least 70% of alerts; the fact-check found nothing; an abstention is low confidence and considered alternatives. It writes `(:Agent {name:'Auditor'})-[:WROTE]->(:Audit {verdict, checks})-[:AUDITS]->(:Decision)`. It cannot change the verdict; disagreement is shown to the human.

## 22. Testing FalkorDB itself (Oct 17)

`bench/fuzz_falkordb.py` builds 2,000 small random graphs and compares FalkorDB's answers with NetworkX or a
brute-force path enumeration: variable-length patterns with and without a path variable, unbounded reachability,
`shortestPath`, `algo.BFS`, `algo.WCC`, `algo.pageRank`, `algo.betweenness`, `algo.SPpaths`, `algo.MSF`. Three
differences were shrunk to 3- or 4-node graphs (`bench/falkordb_repros.py`) and written up in FALKORDB_FINDINGS.md.
The repros are `xfail(strict=True)` tests, so CI notices when a FalkorDB release fixes one. `algo.betweenness`
turned out to be a sampled estimate, so `critical_services` now computes exact betweenness (Brandes, in
`backend/tools/centrality.py`) over the edges it reads from FalkorDB. Our variable-length query shapes were checked
to be on the safe side of the other two findings (`test_our_query_shapes_are_not_affected_by_f1`).

## 23. The PyPI and npm worlds (Oct 17)

`scripts/fetch_pypi.py` snapshots public PyPI metadata for the 15,000 most-downloaded packages (requirements and
the upload time of every release). `backend/world/pypi.py` loads it with the same labels as the company worlds:
packages are `Service`, required dependencies are `DEPENDS_ON {kind:'sync'}`, releases are `Deploy`. That is
1.2 M nodes and 1.29 M relationships, loaded in about 30 s. `backend/tools/supply_chain.py` (`suspect_releases`)
answers "which release in the last 48 hours explains these failing packages?" with one Cypher query, and
`bench/pypi_incidents.py` replays 21 real incidents on it (ECOSYSTEMS.md). `scripts/fetch_npm.py` and
`backend/world/npm.py` do the same for npm: 50,000 packages and 5.5 M releases, with 10 real incidents in
`bench/npm_incidents.py` (colors.js, ua-parser-js, node-ipc, event-stream, …). It is a benchmark and MCP world, not a web
world: 15,000 nodes do not fit on one screen, and per-visitor copies of a 600 MB graph would not fit the free tier.

## 24. Beat the agents (Oct 17)

After a break, a visitor can click a service and lock in a guess (`POST /api/guess`). Guesses close when the agents
start. When the investigation ends, the server compares guess, verdict and the hidden truth, writes a
`Round` node into a shared `scoreboard` graph (outside the per-visitor sandboxes, so it is shared by everyone), and
sends a `game` event with the running totals (`GET /api/scoreboard`).

Also: `GET /api/ready` checks that the database answers, and the web screen polls it on load ("Waking up the
server…") instead of hanging while a free-tier server cold-starts. The database client now has socket timeouts.
